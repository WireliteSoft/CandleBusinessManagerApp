1. CURRENT PROJECT ARCHITECTURE

Frontend
- Vite 5 + React 18 + TypeScript + Tailwind.
- The frontend calls relative /api endpoints through src/lib/api/*.ts. This is good: the
  browser API contract can remain mostly unchanged after the backend moves to a Worker.
- The production frontend currently builds to dist/.

Backend
- Node/Express application in server/index.js with 222 registered route handlers.
- Authentication, authorization, public storefront, admin, teams, catalog, operations,
  billing, Square, PayPal, webhooks, uploads, and email run in the same long-lived Node process.
- Zod schemas in server/schemas/index.js can be retained.

Database topology
- Prisma is configured for SQLite in prisma/schema.prisma.
- One master SQLite database stores global accounts, account users, sessions, billing,
  super-admin data, bans, and global records.
- One separate SQLite database is created for every business account. The current storage
  directory has five account databases.
- Current approximate source data sizes:
  * master database: 20 MB
  * account databases combined: about 11 MB
- server/lib/accountDb.js dynamically creates and caches one Prisma client per account.
- server/index.js uses AsyncLocalStorage plus a Proxy to make the current account database
  appear as the default Prisma connection.

Persistent files and blobs
- Local persistent folders are storage/store-media and storage/store-fonts.
- Express currently publishes those folders through /store-media and /store-fonts.
- Storefront uploads use server/routes/storefrontRoutes.js and write files with node:fs.
- Several database fields also contain image data or data URIs, including product images,
  employee pictures, mold images, storefront logo/banner/background, and appeal evidence.

Node-only or server-state dependencies
- express, cors, PrismaClient, AsyncLocalStorage, node:fs, node:path, process.cwd(),
  process.env, app.listen(), and an in-memory public write rate-limit Map.
- nodemailer SMTP transport in server/lib/storeEmail.js.
- Square Node SDK and PayPal REST calls in payment routes.
- Webhook handlers use Express raw-body middleware and Node Buffer.
- Tests start a separate Node process, use local SQLite files, and call Prisma directly.

Large conversion hotspots
- server/routes/protectedAuthRoutes.js: 1,052 lines.
- server/routes/publicRoutes/storeCommerceRoutes.js: 878 lines.
- server/routes/storefrontRoutes.js: 768 lines.
- server/lib/init/accountTables.js: 706 lines of schema setup.
- Prisma schema: 584 lines.
- Customer account UI: 1,311 lines; frontend-only and not blocked by Cloudflare.


2. RECOMMENDED TARGET ARCHITECTURE

Use one Cloudflare Worker application, not separate Pages and Express deployments.

Worker responsibilities
- Serve the Vite SPA through Workers Static Assets.
- Route /api/* requests through Worker handlers.
- Bind one primary D1 database as DB.
- Bind one R2 bucket as STORE_MEDIA.
- Use Cloudflare secrets for payment, email, and admin credentials.
- Use a Queue for transactional email and other non-critical post-request tasks.
- Add Cron Triggers later for reservation expiration, subscription reminders, cleanup, and
  retryable maintenance work.

Recommended data model: one D1 database with account_id scoping
- Do NOT reproduce the current runtime-created SQLite file per account as the first Cloudflare
  design. A Worker receives named bindings, while the current code chooses a database file at
  runtime and caches Prisma clients. That pattern does not translate cleanly to a D1 binding.
- Create one D1 database containing the master tables and all account tables.
- Add NOT NULL account_id to every current account-owned table.
- Add account_id to every account-owned unique key and index. Example: StoreCustomer email
  becomes UNIQUE(account_id, email), and StoreOrder order_number becomes
  UNIQUE(account_id, order_number).
- Keep global tables without account_id: Account, AccountUser, AuthSession, BillingConfig,
  BillingCheckoutSession, global admin/ban data, and any truly global fragrance catalog data.
- Every account-facing repository method must accept accountId explicitly and bind it in every
  query. There must be no implicit current-account database or global mutable database client.
- This is safe for the current data volume and well below D1's 10 GB per-database ceiling.
- If account growth later requires physical tenant isolation, plan that as a second project with
  a deliberate account-to-database routing registry. Do not add that complexity before it is
  needed.

R2 media design
- Replace local storage/store-media and storage/store-fonts with R2 object keys.
- Suggested object-key layout:
  * accounts/{accountId}/media/{uuid}.{extension}
  * accounts/{accountId}/fonts/{uuid}.{extension}
  * accounts/{accountId}/evidence/{uuid}.{extension}
  * system/giftcard.png
- Add a MediaObject table to D1 if uploads need ownership, MIME type, size, created time,
  visibility, and deletion tracking.
- Move base64/data-URI images out of D1 as part of import. Save an R2 key or Worker media URL
  instead. This avoids large request bodies, row bloat, slow D1 serialization, and memory use.
- Public storefront images may be served by a Worker /store-media/* route with cache headers or
  by a carefully configured public R2 custom domain. Private evidence must remain Worker-gated.


3. REQUIRED BACKEND CONVERSIONS

3.1 Replace Express with a Worker router
- Replace server/index.js with src/worker.ts or worker/index.ts using the Fetch API.
- Hono is a reasonable optional router choice, but plain Worker fetch routing is also valid.
- Convert Express request/response usage to Request, Response, Headers, and Response.json().
- Replace app.use middleware with explicit Worker middleware functions for CORS, JSON parsing,
  error translation, authentication, account scope, feature permissions, and rate limiting.
- Preserve every current public URL and HTTP method first. This prevents frontend rewrites from
  being mixed into the infrastructure conversion.
- Serve the SPA fallback only after API and R2 media paths are handled.

3.2 Replace Prisma and raw SQLite access with a D1 repository layer
- Remove @prisma/client, prisma CLI generation, PrismaClient construction, and DATABASE_URL.
- Add a small database adapter/repository layer. Required operations:
  * first(sql, values) for one row.
  * all(sql, values) for a result set.
  * run(sql, values) for mutations.
  * batch(statements) for grouped writes.
- Use env.DB.prepare(sql).bind(...values) for all variable input. Do not concatenate customer,
  account, table, or identifier values into SQL.
- Convert every Prisma $queryRaw and $executeRaw tagged query manually. This repo has heavy raw
  SQL usage in auth, storefront commerce, super-admin, team, and operations routes.
- Convert current Prisma transactions to D1 batch calls where the statements can be grouped.
  For order creation, stock reservation, gift-card redemption, and payment finalization, define
  idempotency keys and test transaction semantics before release.
- Replace date conversion helpers with explicit ISO 8601 TEXT storage or integer epoch storage.
  Do not rely on Prisma DateTime conversion behavior.
- Retain SQLite-compatible SQL only after testing it against D1. Remove startup PRAGMA commands,
  Prisma-specific behavior, and assumptions about local connection lifetime.

3.3 Remove account database selection and process caches
- Delete server/lib/accountDb.js, accountPrismaCache, AsyncLocalStorage, Prisma Proxy routing,
  getAccountPrisma(), and filesystem account database deletion.
- Replace deleteAccountDatabase(accountId) with a D1 transactional/account-scoped deletion plan
  and R2 prefix deletion job. Do not delete completed accounting records if retention rules apply.
- Update every route context dependency that currently expects prisma/masterPrisma/accountPrisma.
  It should receive env.DB and an explicit auth.account_id instead.

3.4 Replace schema-on-startup with versioned D1 migrations
- Convert server/lib/init/coreTables.js, accountTables.js, and legacyUpgrades.js into ordered
  migrations under migrations/0001_*.sql, migrations/0002_*.sql, and so on.
- Never run CREATE TABLE or ALTER TABLE migrations on every live request or Worker startup.
- Preserve foreign keys, indexes, unique constraints, and current defaults.
- Create an inventory of every table from both the master and account SQLite files before writing
  migrations. The Prisma schema is not the only source of truth because legacy upgrade scripts
  add more tables and columns.
- Replace super-admin sqlite_master inspection with an explicit allow-listed schema catalog or
  D1-compatible metadata inspection. Never expose arbitrary SQL execution to a browser.

3.5 Convert uploads and static media
- Remove Express static middleware and node:fs/path writes.
- Change storefront image/font upload endpoints to validate MIME type, extension, byte size, and
  account ownership, then write an R2 object.
- Replace src/components/storefrontBuilder/assetUtils.ts base64 upload paths with either:
  * Worker-mediated multipart uploads for small files, or
  * direct R2 signed upload URLs for larger assets.
- Preserve the current 8 MB JSON/API limit only where still appropriate. Prefer binary uploads;
  base64 adds unnecessary payload size.
- Move public/giftcard.png to public assets if it is a fixed app asset, or store it in R2 only if
  owners must replace it.

3.6 Convert authentication and security
- Replace process.env use with typed Worker env bindings and Wrangler secrets.
- Remove dangerous code defaults, especially the fallback super-admin email/password in
  server/index.js. Production must fail closed when required secrets are absent.
- Replace the in-memory publicWriteRateBuckets Map. It is per-isolate and cannot enforce a
  global limit. Use a Durable Object for strict IP/user rate limiting, or Cloudflare WAF/rate
  limiting rules for edge enforcement.
- Replace socket IP access with Cloudflare request headers/metadata only after configuring the
  Worker behind Cloudflare. Do not trust arbitrary forwarded headers.
- Retain password hashes and verify legacy hashes during migration. Choose a Worker-compatible
  password implementation and write tests against existing hashes before changing algorithms.
- Store auth sessions in D1 initially; rotate tokens, set expiration, and continue using secure
  Authorization headers or move deliberately to secure HttpOnly cookies.
- Revalidate all account_id ownership checks after consolidation. Account isolation is the most
  important regression risk in this conversion.

3.7 Payments, webhooks, and email
- Square and PayPal REST calls can remain server-side Worker fetch calls. Keep provider secrets
  in Wrangler secrets, never in Vite variables or browser responses.
- Evaluate removing the Square Node SDK in favor of Square's HTTPS APIs and Web Crypto webhook
  verification. This avoids relying on Node compatibility and reduces Worker bundle risk.
- Replace Node Buffer base64 operations with Web APIs or Worker-compatible helpers.
- Convert Express raw webhook middleware to request.arrayBuffer() or request.text() and verify
  signatures against the untouched body.
- Keep PaymentWebhookEvent/provider event uniqueness in D1 for idempotent webhook processing.
- Do not mark an order paid based only on a client success response. Preserve provider capture
  and webhook reconciliation as authoritative paths.
- Replace nodemailer SMTP with an HTTP transactional-email provider. Queue emails and retries
  with Cloudflare Queues so a slow provider does not delay checkout or route responses.
- Convert StoreEmailEvent to a durable outbox: insert event in D1 with the business mutation,
  enqueue after commit, and update its delivery state from the queue consumer.

3.8 Background and scheduled work
- The current backend has no production server cron. Some UI polling/timers are browser-only and
  can remain unchanged.
- Add Workers Cron Triggers for expired order reservations, pending checkout cleanup, subscription
  fulfillment reminders, back-in-stock delivery retries, stale sessions, and R2 orphan cleanup
  only after the core migration works.
- Use Queues for emails, optional media processing, migration backfills, and long fan-out work.
- Keep Worker request handlers short; do not scrape catalogs, import large files, or scan all
  accounts inside a normal customer request.


4. DATABASE MIGRATION PLAN

Phase A - Inventory and backup
1. Stop writes during the final migration window, or implement a temporary read-only mode.
2. Copy storage/master/candles-business.db, every storage/accounts/*.db, all R2 candidate media,
   .env key names (not secret values), and migration logs to encrypted offline backups.
3. Record row counts for every source table and per-account table.
4. Record source checksums and create a migration audit report.

Phase B - Build target schema
1. Create a D1 development database and production database.
2. Write a normalized baseline migration that combines master and account tables.
3. Add account_id and compound indexes to all tenant tables.
4. Add migration metadata: source_database, source_account_id, source_primary_key, migrated_at.
5. Add data integrity constraints before importing production data.

Phase C - Build a one-time Node import tool
- Keep this tool outside the Worker because it needs read access to the existing local SQLite files.
- Use the current Prisma/SQLite reader only for this one-time import utility, or use a local
  SQLite export tool.
- Import master rows first: accounts, users, sessions, billing, bans, roles, and global catalog.
- Import account rows second, adding the owning account_id to every row.
- Maintain original IDs where possible so existing foreign-key relations and URLs remain valid.
- Upload media to R2 before or during row import and replace old file/data-URI references.
- Chunk imports well below Worker/D1 request limits. Use Wrangler D1 execute/import workflows or
  an authenticated bulk-import Worker endpoint designed for resumable batches.
- Make the importer idempotent and resumable. It must be safe to re-run a failed batch.

Phase D - Verify imported data
- Compare counts by account and table.
- Verify logins for owner, employee, admin, super-admin, and storefront customer accounts.
- Verify product images, fonts, storefront logo/banner/background, and uploaded assets resolve
  from R2.
- Verify gift-card balances, customer credits, reward totals, order totals, stock reservations,
  subscriptions, and billing sessions.
- Verify public storefront slugs resolve to the correct account only.
- Verify one account cannot access another account's data through every protected endpoint.

Phase E - Cutover and rollback
- Deploy a staging Worker against a staging D1/R2 copy first.
- Point a staging hostname at the Worker and run full API/browser payment sandbox tests.
- During production cutover: block writes, run final delta import, validate counts, deploy Worker,
  configure routes/custom domain, then re-enable writes.
- Keep the old local deployment and immutable SQLite backups available until acceptance testing
  and a documented rollback window have passed.

9. IMPORTANT RISKS AND DECISIONS

HIGH RISK: Account isolation
- Consolidating tenant databases is the correct first step but requires account_id on every query,
  index, unique constraint, and foreign-key path. Missing one condition can expose data across
  businesses. Build automated isolation tests before importing production data.

HIGH RISK: Commerce mutations
- Checkout, stock reservation, gift-card redemption, customer credits, payment capture, refunds,
  and webhook reconciliation require careful idempotency and D1 transaction/batch tests.

HIGH RISK: Media migration
- Database data URIs and storage file URLs must be catalogued and migrated to R2 without broken
  storefront images. Do not delete local media until automated URL verification passes.

HIGH RISK: Admin database explorer
- The current super-admin tooling inspects SQLite metadata. It must not become arbitrary D1 SQL
  access from a browser. Use an allow-listed admin API with role checks and audit logging.

MEDIUM RISK: Node compatibility
- Workers supports a subset of Node APIs, but its filesystem is virtual/in-memory and cannot be
  used for persistent account databases or uploads. Treat Node compatibility as a migration aid,
  not a reason to carry Express/Prisma/filesystem architecture into production.

MEDIUM RISK: Email and webhooks
- SMTP/nodemailer and Express raw-body middleware need deliberate replacements. Test real provider
  sandbox callbacks before enabling production billing.

DECISION REQUIRED BEFORE IMPLEMENTATION
- Confirm the account model: recommended single D1 with account_id versus a later tenant-sharded
  D1 approach. This plan assumes the recommended single D1 model.
- Choose the transactional email provider.
- Decide whether public assets use a Worker media route or an R2 custom domain.
- Decide whether strict rate limiting needs Durable Objects or can use Cloudflare WAF/rate rules.
- Confirm a staging Cloudflare account/domain and production cutover window.


10. IMPLEMENTATION ORDER

1. Create staging Cloudflare resources and Wrangler configuration; do not touch production data.
2. Add Worker entrypoint, static asset serving, typed env bindings, and /api/health.
3. Create D1 schema migrations for the consolidated account_id model.
4. Build D1 repository helpers and migrate authentication/account scope first.
5. Migrate core operations routes: products, supplies, recipes, calculators, batches, teams.
6. Migrate storefront setup and all R2 upload/media routes.
7. Migrate public storefront, customers, orders, gift cards, rewards, and fulfillment flows.
8. Migrate Square/PayPal payment and webhook paths, then run sandbox tests.
9. Add email queue/outbox, rate limit implementation, cron jobs, logs, and backups.
10. Build importer, import staging data, run complete tests, then schedule production cutover.
